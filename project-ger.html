Group Emotion Recognition
for Smart Park Monitoring

A collaborative IoT-cloud system that recognises the dominant emotional state of visitor groups in the Parco Nazionale della Sila. Raspberry Pi 5 edge nodes with on-device face detection feed a fine-tuned Moondream2 Vision-Language Model running on AWS, queried through a Flutter app over a private Tailscale network. Built with a team of four as a joint IoT and Cloud/Edge Computing examination.

University Context

This project was developed as part of the joint examination of IoT Device Programming and Distributed Systems and Cloud/Edge Computing (A.A. 2025/2026) at the degree programme in Telecommunications Engineering. The team — Gianluca Perrotta, Marco Macrì, Orazio Ruberto, and Asrar Jemal Mohammed — designed and implemented the complete system from requirements analysis through cloud deployment and EdgeCloudSim simulation.

The Parco Nazionale della Sila (Calabria, 73,695 ha) was chosen as the application scenario: a real-world environment where park management lacks objective, real-time tools to assess how visitors emotionally perceive the natural environment.

Objectives

FR1 – FR2

Edge Frame Acquisition

Use on-edge face detection (OpenCV DNN SSD) on a Raspberry Pi 5 + GoPro node to decide when to capture and transmit a frame — every 20 s while the same group stays in view, immediately when a new person enters.

FR3 – FR4

VLM Emotion Classification

Classify the dominant group emotion (8 classes, FER+) using a fine-tuned Moondream2 VLM served behind a two-queue priority system on the cloud GPU instance.

FR5

Persistent Cloud Storage

Store inference results (emotion label, node, timestamp) in a MySQL database co-located with the backend on the EC2 instance.

FR6 – FR7

Mobile Dashboard & NL Queries

Let park workers query emotion percentages per node and time range, analyse on-demand photos, and ask natural-language questions answered by an AI agent — all from a Flutter app secured via Cognito.

NFR5

VLM Benchmarking

Fine-tuned PaliGemma 2, MiniCPM-V, and Moondream2 with QLoRA on FER+; Moondream2 selected for deployment.

NFR2

Offloading Simulation

Validate scalability of the offloading pipeline using EdgeCloudSim with 1–10 concurrent nodes and three routing policies.

System Architecture

Three-tier device–edge–cloud architecture over a private Tailscale network. The Raspberry Pi handles only face detection and frame transmission; all VLM inference, storage, and the AI agent run on a single GPU instance in the cloud. Two separate Cognito authentication flows secure the two client types: JWKS-cached M2M Client Credentials for Raspberry Pi nodes, and Cognito GetUser for Flutter app users.

MySQL schema — detections table: id, node_name, num_persone, emotion (nullable), timestamp (BIGINT). AWS S3 stores scripts, training datasets, and model artefacts. No API Gateway and no DynamoDB keep the full deployment within the $150 budget.

Backend API

FastAPI backend on the EC2 instance (port 8080), reachable only through the private Tailscale network.

Method Endpoint Description
POST /emonodes/sendmessage Raspberry Pi sends a frame; two-phase DB write records the detection, then Moondream2 classifies the dominant emotion via the normal-priority VLM queue and updates MySQL.
GET /app/data/getbetweendates Returns per-node emotion percentage aggregation for a given time range.
POST /app/analyzephoto App sends a base64-encoded photo (JPG/PNG/JPEG); routed to the VLM's high-priority queue (weight=3) and returns the detected emotion.
POST /app/askagent Natural-language question is forwarded to the Silvan AI agent, converted into a SQL query, and answered in natural language.

Methodology

The project followed a structured analysis → design → implementation workflow using ACOSO-METH notation for IoT domain modelling (SO-centric and IoT Service-centric models). Key design decisions were documented with traceability to functional and non-functional requirements.

DESIGN

VLM over CNN

Vision-Language Models simultaneously classify the dominant emotion and generate a natural-language description, providing richer output than a CNN label-only approach.

DESIGN

Cloud Offloading

Raspberry Pi 5 lacks a dedicated GPU; running multi-billion-parameter VLMs locally would violate the latency constraint. All inference is delegated to a single EC2 g4dn.xlarge, reached over a private Tailscale network instead of a public API Gateway.

DESIGN

PEFT Benchmark & Model Selection

Three VLMs are evaluated on FER+ (with and without QLoRA fine-tuning). PaliGemma 2 overfit during fine-tuning; its base model was kept as a comparison baseline. Moondream2, fine-tuned with QLoRA, reached the best accuracy and was selected for deployment. MiniCPM-V and Moondream2 were QLoRA fine-tuned by the respective team members.

DESIGN

Single Backend, Two-Queue Priority

A single FastAPI process exposes ingestion, on-demand analysis, historical queries, and the natural-language agent as independent async endpoints. A two-queue priority scheduler keeps interactive app requests from waiting behind the steady stream of Raspberry frames.

Dataset — FER+

All three VLMs were benchmarked and fine-tuned on the FER+ dataset.

8-CLASS SCHEMA

Full Emotion Set

~78,000 facial images across 8 emotion classes: happiness, neutral, surprise, anger, sadness, disgust, fear, contempt. Original images are 48×48 px grayscale, resized to 224×224 RGB for VLM input.

4-CLASS SCHEMA

Distress Variant

Five low-frequency negative emotions (anger, sadness, disgust, fear, contempt) merged into a single distress class, eliminating minority-class imbalance. Used for the PaliGemma 2 baseline comparison to show the effect of class consolidation without any model change.

My Personal Contributions

FASTAPI BACKEND

FastAPI Backend — Sole Implementation

Co-designed with Marco the four REST endpoints and solely implemented the entire backend on EC2 g4dn.xlarge using FastAPI with full async/await support: POST /emonodes/sendmessage (frame ingestion, two-phase DB write, normal-priority VLM queue), GET /app/data/getbetweendates (per-node emotion percentage aggregation), POST /app/analyzephoto (high-priority VLM queue), POST /app/askagent (natural-language query forwarding to Silvan agent).

VLM INTEGRATION

VLM Queue Service Integration

Integrated Marco's fine-tuned Moondream2 and model_queue_service.py into the FastAPI startup lifecycle. Model loaded onto GPU once at startup; endpoint_one (normal priority) serves Raspberry Pi frame requests, endpoint_two (weight=3) serves app photo analysis requests.

AI AGENT INTEGRATION

Silvan AI Agent Integration

Integrated Orazio's Silvan agent (llama3.2 via Ollama, text-to-SQL, four-stage pipeline) as a direct Python import via sys.path. Offloaded via asyncio.to_thread to keep the event loop free. Warmup call at startup eliminates the ~30 s cold-start penalty on the first query.

MQTT INTEGRATION

MQTT Digital Twin Integration

Integrated Marco's MQTTService.py publisher. Broker configured from .env via publisher.set_info(). After each VLM classification, the detection is forwarded in Eclipse Ditto format inside a try/except block — MQTT failures never affect the 200 OK response to the Raspberry Pi.

TAILSCALE VPN

Tailscale VPN Infrastructure

Configured the private Tailscale mesh network (proposed by Marco) connecting Raspberry Pi nodes and the Flutter app to the EC2 backend, replacing AWS API Gateway (~$24/month) to stay within the $150 project budget. The mesh eliminates the need for a public IP on the Raspberry Pi nodes.

AWS INFRASTRUCTURE

AWS Infrastructure & Cognito Auth

Configured and managed EC2 g4dn.xlarge (NVIDIA Tesla T4, 16 GB VRAM, eu-west-1) with MySQL on the same host (zero extra cost), detections table schema, and instance auto-shutdown policy. Provisioned AWS Cognito User Pool (app users) and M2M Client Credentials (Raspberry Pi nodes) — two separate authentication flows. AWS S3 stores scripts, datasets, and model artefacts.

SYSTEM TESTING

End-to-End System Testing

End-to-end tested all four endpoints with real data on the live EC2 instance using valid Cognito tokens, verifying response correctness against MySQL. Confirmed JPG, PNG, and JPEG formats all working for photo ingestion.

VLM FINE-TUNING & EVALUATION

PaliGemma 2 — Fine-tuning & Evaluation

Fine-tuned PaliGemma 2 (3B) on FER+ using QLoRA (4-bit NF4, LoRA r=4, multiple learning rates) on EC2 g4dn.xlarge. All runs produced rapid, irrecoverable overfitting — PaliGemma 2's SigLIP encoder was already pre-trained on facial data at scale, leaving no meaningful gap for supervised fine-tuning to close. Deployed the base model with a minimal direct prompt: 69.1% accuracy, 0.436 Macro F1 (8-class); 69.5% accuracy, 0.691 Macro F1 (4-class distress); 0.00% invalid predictions.

EdgeCloudSim — Offloading Policies

10-hour simulation with 1–10 concurrent cameras. Task failure rate: 0%. Service time: ~2.15 s (stable across node counts). Edge utilisation: 7.6% at 1 node → 78.9% at 10 nodes.

ALWAYS_CLOUD

All tasks → EC2

Lowest failure rate; higher average latency under peak load.

RANDOM

Random assignment

Baseline comparison; moderate performance across metrics.

PREDICTIVE

Load-aware routing

Best latency/reliability trade-off under varying node count.

Simulation parameters: max delay 5 s · task interarrival 3 s (Poisson) · frame upload ~100 KB · duration 10 h. Metrics: average service time, task failure rate, network delay, processing time.

Budget

The full system was deployed and operated within a total budget of $150. Two cost-cutting decisions were key:

NO API GATEWAY

Tailscale replaces AWS API Gateway

Using a private Tailscale mesh instead of AWS API Gateway saves ~$24/month. The Raspberry Pi nodes and Flutter app connect directly to the EC2 backend through the encrypted tunnel.

NO DYNAMODB

MySQL co-located on EC2

Running MySQL on the same EC2 host as the FastAPI backend incurs zero additional cost, replacing a managed DynamoDB instance that would have added to the monthly bill.

Conclusions

The GER system addresses all defined requirements through a distributed IoT-cloud architecture. Edge-triggered frame capture, VLM-based emotion classification, persistent storage in MySQL, secure mobile access over Tailscale and Cognito, MQTT Digital Twin forwarding in Eclipse Ditto format, and a natural-language query agent are fully integrated in the implemented pipeline.

A key finding from my work on PaliGemma 2 is that QLoRA fine-tuning was counterproductive: the model's SigLIP encoder was already pre-trained on facial data at scale, so every fine-tuning run overfit rather than generalised. The base model with a minimal prompt outperformed all fine-tuned checkpoints, achieving 69.1% accuracy, 0.436 Macro F1 (8-class) and 69.5% accuracy, 0.691 Macro F1 (4-class distress), with 0.00% invalid predictions. The distress class consolidation — merging five low-frequency negative emotions into one — raised Macro F1 by +0.255 without any model change.

Moondream2 (Marco Macrì), fine-tuned with QLoRA (1 epoch, 1/3 of data), was selected for production deployment after reaching 82.2% accuracy, 0.632 Macro F1, and 0.00% invalid predictions on the 8-class FER+ benchmark — the best result among the three VLMs. MiniCPM-V 4.6 (Orazio Ruberto) achieved 74.8% accuracy and 0.567 Macro F1 with 0.00% invalid predictions. Both models show strength on dominant classes (happiness F1 ~0.92) and weakness on minority classes (contempt, disgust). The comparative benchmark provides an objective, data-driven basis for the model selection.

EdgeCloudSim validated the scalability of the offloading pipeline: 0% task failure across a 10-hour simulation with 1–10 concurrent nodes, stable service time of ~2.15 s, and edge utilisation scaling from 7.6% to 78.9% as nodes increase.

Planned future developments include short video-clip analysis for improved temporal consistency, anomaly alert notifications in the mobile app, and domain-specific fine-tuning on images collected directly within the park.
