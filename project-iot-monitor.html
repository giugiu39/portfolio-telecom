IoT Environmental Monitor
with MQTT & Node-RED Dashboard

An ESP32-based sensor network that acquires environmental data — temperature, humidity, GPS coordinates and wind speed — and transmits it in real time to a Node-RED dashboard via MQTT. Network performance over 4G/5G NSA was analysed with Wireshark.

← Back to projects

University Context

This work was developed as the Bachelor's thesis for the degree in Computer Engineering at Università della Calabria (UNICAL), A.Y. 2024/2025. The thesis is titled "Progettazione e implementazione di un sistema di monitoraggio e controllo remoto basato su tecnologie IoT e radiomobili" (Design and Implementation of a Remote Monitoring and Control System Based on IoT and Mobile Radio Technologies).

The project explores a complete IoT pipeline: from hardware sensor reading on a microcontroller, through a publish-subscribe messaging layer, up to a visual flow-based controller with live dashboard — all tested on real cellular networks.

Objectives

HARDWARE

Sensor Integration

Build a multi-sensor circuit on ESP32 that reads temperature/humidity (DHT22), geographic coordinates (NEO-6M GPS), and wind speed (WH-SP-WS01 anemometer) every 5 seconds.

COMMUNICATION

MQTT over Wi-Fi

Transmit all sensor readings to an MQTT broker (Mosquitto locally or HiveMQ Cloud over TLS) using a structured topic hierarchy under esp32/sensori/.

AUTOMATION

Node-RED Controller

Process incoming MQTT data with a Node-RED flow (Docker-deployed) to build a live dashboard, event-driven alerts via Telegram bot, and extensible automation logic.

NETWORK ANALYSIS

4G/5G NSA Benchmarking

Connect the ESP32 via mobile hotspot and capture MQTT traffic with Wireshark across four network configurations (4G/5G × 5/20 MHz) to measure RTT latency and throughput.

System Architecture

The system follows a classic IoT three-layer pipeline: a physical sensing layer (ESP32 + sensors), a messaging layer (MQTT broker), and a processing/visualisation layer (Node-RED on Docker). The broker and Node-RED can be co-located on a PC in the local network, or the broker can be moved to HiveMQ Cloud for remote access over TLS.

Hardware — Distribution Module

The ESP32 is the central unit: it reads all sensors, encodes the data and publishes it to the MQTT broker every 5 seconds. The anemometer uses hardware interrupts (ISR) to count reed-switch pulses; wind speed is derived from pulse frequency using the sensor's datasheet formula.

Complete circuit: ESP32 + NEO-6M GPS + DHT22 + WH-SP-WS01 anemometer on breadboard

MQTT Topic Structure

Each sensor value is published to a dedicated leaf topic at 5-second intervals. The hierarchical structure makes selective subscription straightforward (e.g. esp32/sensori/# subscribes to all sensors at once).

Node-RED Flow & Dashboard

Node-RED subscribes to all sensor topics and routes each value through a dedicated flow: JSON parsing → gauge/chart node → dashboard UI. Each sensor category has its own dashboard page. Alarm thresholds trigger a Telegram bot notification. Node-RED runs in a Docker container, making it portable across any host on the network.

Node-RED visual flow — MQTT subscribe nodes → processing → dashboard gauges for DHT22, GPS and anemometer

Development Process

The project was built incrementally through structured practice steps, each adding a new layer of complexity before full integration.

STEP 1–2

ESP32 Setup & Wi-Fi

Installed ESP32 board in Arduino IDE, uploaded first sketch, and implemented Wi-Fi connectivity using the WiFi.h library.

STEP 3–5

Individual Sensor Drivers

Developed and validated each sensor driver: DHT22 via digital pin, NEO-6M GPS via UART2 with TinyGPSPlus, anemometer via hardware interrupt pulse counting.

STEP 6–7

Sensor Fusion & MQTT

Combined all sensors in a single sketch with a 5-second publish loop. Connected to Mosquitto (local, port 1883), then migrated to HiveMQ Cloud with TLS (port 8883) and NTP sync.

STEP 8

Node-RED Integration

Built the full Node-RED flow in Docker: MQTT subscribe → JSON parse → dashboard gauges for each sensor page + Telegram alarm bot for threshold events.

STEP 9

Network Testing

Tethered the ESP32 via smartphone hotspot to 4G/5G NSA. Captured 600-second Wireshark traces on port 8883 across four configurations. Analysed RTT and throughput with TShark filters.

THESIS

Protocol Study

Studied and documented MQTT internals: publish-subscribe architecture, topic hierarchy, QoS levels (0/1/2), retain messages, Last Will & Testament, Keep Alive, and the TCP/IP foundation layer.

Network Performance Results

MQTT traffic was captured with Wireshark over 600-second sessions on port 8883, filtering only TCP traffic between the ESP32 and the HiveMQ Cloud broker. The ESP32 connected via mobile hotspot to test four 4G/5G NSA configurations. RTT was extracted from tcp.analysis.ack_rtt; throughput from total bytes ÷ duration.

Summary Table

Network Bandwidth Avg RTT (ms) Avg Throughput (kbps)
4G LTE 20 MHz 58.7 ~30.0
4G LTE 5 MHz 117.5 27.6
5G NSA 20 MHz 110.5 26.4
5G NSA 5 MHz 105.6 28.0

Key observation: 4G 20 MHz achieves the best latency (58.7 ms) — nearly half that of the other configurations. 5G NSA latency (~105–117 ms) is comparable to 4G 5 MHz because the NSA architecture still relies on a 4G LTE control plane (EPC), limiting the latency advantage. Throughput is uniformly low (~27–30 kbps) across all configs, consistent with the lightweight MQTT IoT payload (few bytes per topic, every 5 s).

Conclusions

The project successfully demonstrates a complete, end-to-end IoT monitoring pipeline: multi-sensor data acquisition on a low-cost microcontroller, reliable real-time transmission via MQTT (both local and cloud broker), and flexible data processing and visualisation with Node-RED.

The network analysis reveals a clear performance hierarchy: 4G 20 MHz offers the lowest latency (58.7 ms) for MQTT traffic. Surprisingly, 5G NSA configurations do not outperform 4G in latency for this use case — a direct consequence of the Non-Standalone architecture, which anchors the control plane on the existing 4G core. Throughput remains consistently low across all configurations (~27–30 kbps), confirming that IoT-scale MQTT traffic does not stress the radio channel and that latency — not bandwidth — is the critical parameter for this type of application.

Possible extensions include integrating an actuator (relay, servo) controlled via downlink MQTT commands, adding a time-series database (InfluxDB) for historical data logging, and testing 5G Standalone (SA) to measure the true latency potential of a native 5G core.
