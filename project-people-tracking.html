Networking Performance Analysis of an
Edge-Based People Tracking IoT System

An edge-based IoT system that detects and tracks people in real time on a Raspberry Pi (YOLO + ByteTrack) and sends lightweight zone-transition events through two heterogeneous architectures — BLE + MQTT/TLS and CoAP/UDP — compared in terms of latency, reliability, security overhead and scalability.

University Context

This work was developed as an academic project for the "Networking Aspects of IoT" course (A.A. 2026/2027) of the M.Sc. in Telecommunications Engineering at Università della Calabria (UNICAL), as part of a four-person team.

The system follows an edge-computing approach: video analysis and people tracking run locally on the Raspberry Pi, and only the resulting semantic movement events (e.g. Person 1053: Zone_A → Zone_D) are transmitted — no video stream ever crosses the network. The project then asks a networking question: how do different communication architectures behave when carrying these compact events?

System Architecture

The testbed has three nodes: the Raspberry Pi (edge tracker and event producer), an ESP32 / Arduino Nano ESP32 (BLE-to-IP gateway) and a MacBook Pro (aggregation and measurement node running the CoAP server and the MQTT subscriber). The same events are routed through two different paths.

Main Implementation

EDGE

Tracker & Zone Events

Python tracker on the Raspberry Pi with YOLO, ByteTrack, a zone-picker utility and zone-transition event generation, plus a variant without AES-GCM.

FIRMWARE

BLE-to-Wi-Fi Gateways

ESP32 and Arduino Nano ESP32 firmware receiving events over BLE and republishing them via MQTT/TLS, with encrypted, unencrypted and QoS-experiment versions.

PATH A

MQTT/TLS & QoS Experiments

Integration with HiveMQ Cloud and dedicated subscribers that measure end-to-end latency for QoS 0, 1 and 2.

PATH B

CoAP Request/Response

aiocoap-based server handling decryption, timestamp extraction, latency computation, persistence and responses used for RTT measurement.

SECURITY

AES-GCM Authenticated Encryption

Each payload carries a 12-byte nonce plus ciphertext and authentication tag, giving confidentiality, integrity and authentication; NO_AES variants isolate its overhead.

BENCHMARK

Stress Testing & Analysis

Python stress tests raising the load from 5 to 50 EPS and a latency-analysis script computing min, mean, p50, p95, p99 and PDR from JSONL logs.

Experimental Evaluation

Both paths were evaluated under controlled conditions with the same events, so differences can be attributed to the communication stack.

Metric How it is measured
End-to-end latency Receive timestamp − send timestamp, assigned just before serialization (application level)
Packet Delivery Ratio Received messages ÷ sent messages × 100
MQTT QoS 0 / 1 / 2 Latency of the full BLE + MQTT path per delivery semantics
CoAP RTT Request → response time measured on the Raspberry Pi
Scalability 5 → 50 EPS; min / avg / p50 / p95 / p99 latency and PDR at each step
AES-GCM overhead Encrypted vs. unencrypted variants of firmware, tracker and servers

Clock synchronization: one-way latency needs aligned clocks, so the Raspberry Pi runs chrony, the MacBook is synchronized via sntp before every session, and no fixed latency correction is applied. Packets were also inspected with Wireshark/TShark.

PATH B

CoAP / LAN

Avoids the BLE gateway and the cloud/WAN segment: in the tested local configuration it showed low latency and high delivery reliability.

PATH A

BLE + MQTT / Cloud

Latency is the combined effect of BLE, gateway processing, Wi-Fi, TLS, MQTT, broker routing and WAN conditions.

LOAD

Saturation

Higher event rates cause queueing, wireless contention and buffer pressure; the stress tests locate degradation and losses experimentally.

Conclusions

The project shows that moving intelligence to the edge turns people tracking into a very light networking problem: only compact events are sent, so the interesting questions become protocol behaviour, security cost and scalability rather than bandwidth.

The direct CoAP/UDP path is simpler and faster on a local network, while BLE + MQTT/TLS adds stages (gateway, Wi-Fi, TLS, cloud broker, WAN) in exchange for remote reach, broker-based distribution and configurable delivery guarantees via QoS. Measured values depend on the specific hardware, firmware, wireless environment, broker region and workload, so they describe this testbed rather than universal protocol benchmarks.
